0. RESUMEN DEL PROBLEMA
-----------------------
- Se ve borroso incluso en el mismo Wi-Fi (180p a 7-10 fps) => parte del
  problema está en la APP, no solo en internet.
- Causas encontradas en el código:
  a) HostPanel.tsx: video.contentHint = 'motion' -> Chrome baja la RESOLUCIÓN
     primero para no perder fluidez -> borroso (peor en texto/páginas).
  b) Chrome arranca en 320x180 y a veces se queda ahí. El "guardián"
     (HostPanel.tsx, refreshAdaptation en lib/webrtc.ts) SOLO actúa si dice
     "limitado por la red" (bandwidth). Si se atora sin razón ("none"), no hace nada.
  c) Se usa VP8 (el códec más viejo).
  d) Conexión "malla" (mesh): la PC manda un video POR CADA espectador y el
     video va directo México -> Argentina (o por TURN, que solo reenvía).


1. COSTO (verificado hoy en la documentación de Cloudflare)
-----------------------------------------------------------
- SFU y TURN comparten 1000 GB GRATIS al mes (lo que Cloudflare ENVÍA).
- Después: $0.05 USD por GB.
- Estimado: 2 espectadores x ~2.5 Mbps x 2 h = ~4.5 GB por película.
  => ~200 películas al mes gratis. Sobra.
- Recomendación: en Cloudflare, poner alerta de uso/facturación por si acaso.


2. CÓMO FUNCIONA EL SFU (resumen técnico)
-----------------------------------------
- API: https://rtc.live.cloudflare.com/v1/apps/{APP_ID}/...
  Header: Authorization: Bearer {APP_SECRET}   (el secreto SOLO en el servidor)
- Endpoints:
    POST /sessions/new                         -> { sessionId }
    POST /sessions/{id}/tracks/new             publicar (local) o recibir (remote)
    PUT  /sessions/{id}/renegotiate            mandar la "answer" del navegador
    PUT  /sessions/{id}/tracks/update          cambiar capa de simulcast (preferredRid)
    PUT  /sessions/{id}/tracks/close           cerrar tracks
    GET  /sessions/{id}                        ver estado
- PUBLICAR (anfitrión):
    1. pc.addTransceiver(track, { direction: 'sendonly', sendEncodings: [...] })
    2. createOffer + setLocalDescription, ESPERAR a que termine de juntar ICE.
    3. Servidor: sessions/new, luego tracks/new con
       { sessionDescription: offer, tracks: [{ location:'local', mid, trackName }] }
    4. Navegador: setRemoteDescription(answer). (No necesita renegotiate.)
- RECIBIR (espectador):
    1. pc nueva + ontrack. Servidor: sessions/new (sesión propia del espectador).
    2. tracks/new con
       { tracks: [{ location:'remote', sessionId: <del anfitrión>, trackName,
                    simulcast: { preferredRid:'f', priorityOrdering:'asciibetical',
                                 ridNotAvailable:'asciibetical' } }] }
    3. Responde una OFFER (requiresImmediateRenegotiation: true):
       setRemoteDescription -> createAnswer -> setLocalDescription -> esperar ICE
    4. Servidor: renegotiate con la answer. Seguir SOLO cuando la API la acepte.
- SIMULCAST: el anfitrión manda 3 capas con rid 'f' (completa), 'h' (mitad),
  'q' (cuarto). Con 'asciibetical' el orden a-z = prioridad (f > h > q).
  OJO: la doc NO garantiza que el SFU cambie de capa solo por ancho de banda
  => el espectador debe medir y pedir otra capa con tracks/update (FASE 5).
- Reglas de la doc: una operación a la vez por sesión (esperar a que termine
  el intercambio SDP antes de la siguiente); revisar errores por cada track
  (errorCode / errorDescription); sesiones sin conectar caducan: crearlas
  justo antes de usarlas. STUN de Cloudflare: stun:stun.cloudflare.com:3478.
- Fuentes:
    https://developers.cloudflare.com/realtime/sfu/get-started/connection-patterns/
    https://developers.cloudflare.com/realtime/sfu/simulcast/
    https://developers.cloudflare.com/realtime/sfu/https-api/
    https://developers.cloudflare.com/realtime/static/realtime-api-2024-05-21.yaml
    https://developers.cloudflare.com/realtime/sfu/platform/pricing/

        entre tarde. Se borra al dejar de compartir o si el anfitrión se va.
[ ] 2.5 'webrtc:config' dice también si el SFU está disponible (sfu: true/false).
[ ] 2.6 Al arrancar, el servidor imprime "SFU: configurado / no configurado".
